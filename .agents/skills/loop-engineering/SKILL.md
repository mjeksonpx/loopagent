# Loop Engineering (bounded loop with proof)

Превращает работу агента в ограниченную петлю, которую принимают по доказательству, а не по
уверенности: `Build → Fail → Repair → Prove → Review → Handoff`.
Разбор механики по курсу — `course/00_mechanics_map.md`, канонический текст — `course/**`.

## Когда включать

- Работа требует нескольких раундов с накоплением evidence (readiness, безопасность, рефакторинг, релиз-гейт).
- Нужны состояние, артефакты раундов, stop-условия и финальный handoff.
- Нужен локальный гейт, который печатает PASS-маркер и `exit 0`.

## Когда НЕ включать

- Одноразовая правка текста/файла без раундов и evidence.
- Задачи, где достаточно `verify-changes` за один проход.
- Настройка расписания/крона как таковая (это автоматизация, а не содержание петли).

## Контракт рана (заполнить до первой правки)

```
Goal:          <что должно стать правдой>
Sources:       <файлы/команды — источник истины, не выдумывать evidence>
Constraints:   <что можно менять; что нельзя: сеть, секреты, вне репо>
Done-when:     python3 scripts/check_loop.py → LOOP_ENGINEERING_PASS_0001, exit 0
Stop-if:       нужного файла нет / нужна сеть или секреты / правка выходит за репо / гейт не зеленеет после 3 раундов
```

## Гейт (Prove)

```bash
python3 scripts/check_loop.py            # обычный режим; опциональные измерения могут SKIP
python3 scripts/check_loop.py --strict   # SKIP становится FAIL (после Этапа 2)
python3 scripts/check_loop.py --report artifacts/loop_gate_report.json
```

Гейт **read-only**: сам ничего не чинит и не пишет (кроме явного `--report`). Стартует красным —
печатает список failures и `LOOP_ENGINEERING_STOP_0001` с `exit 1`; после ремонта — `[OK]` по
измерениям и `LOOP_ENGINEERING_PASS_0001` с `exit 0`. Маркер печатает **только гейт**, не агент.

Guardrail-скан не должен ловить evidence: транскрипты раундов и собственные транскрипты гейта
цитируют текст failures. Поэтому в markdown вызовом считается только строка, начинающаяся с бинаря
агента, а исходник гейта и оба его транскрипта (`artifacts/loop_gate_report.json`,
`artifacts/loop_gate_pass.json`) исключены из скана целиком.

Приёмка проекта — только `--strict`: обычный режим печатает `acceptance: stage-1`, строгий —
`strict-complete`. Якорь `loop_gate_pass.json` пишется, когда зелены **все измерения кроме тех, что
читают сам якорь** — `D05` (связывает handoff с якорем) и `D12` (проверяет подпись якоря); хэш вердиктов
считается без обоих, иначе измерение сертифицировало бы само себя. Из этой пары следует восстановление
потерянного состояния: дерево без якоря не может его выпустить, если `D12` требуется для выпуска —
`D12` ждёт подписи, подпись ждёт якоря, якорь ждёт `D12`. Поэтому первый прогон после смены вердиктов
падает на `D05` (якорь устарел) и на `D12` (подписи нет), хэш из якоря прописывается в handoff, якорь
подписывается, и только следующий прогон даёт fixpoint.

## Цикл

1. **Инспекция + план.** Прогнать гейт, взять список failures как план работ. Правок нет, ждать одобрения.
2. **Один раунд за раз.** Закрыть один gap → обновить `artifacts/loop_state.json` → добавить evidence → записать `artifacts/rounds/round_NN.md`.
3. **Метрики монотонны** в правильную сторону: readiness/evidence растут, risk/blockers падают.
4. **Перепрогон гейта** после значимых изменений; вывод гейта — единственный источник истины.
5. **Ревью отдельным движком:** `ywcrew panel` (codex + grok + agy/claude-sonnet). Оценщик имеет право сказать «нет».
6. **Стоп** только когда гейт печатает PASS-маркер. Затем — короткий handoff.

## Контекст и итерации (свежий контекст против `/loop`)

Правило взято из Ralph Loop (раздел 5 курса) и проверено на собственной практике: итерация должна
начинаться с **чистого контекста**, а память между итерациями живёт в файлах, не в окне модели.

- **Поток задач** (N карточек) идёт только через очередь: каждая карточка — новый процесс, свежий
  контекст, бриф вместо накопленной истории. Воркер не помнит прошлую карточку и не должен.
- **`/loop` в сессии** крутит тот же контекст: модель тащит свои прошлые правки, окно растёт, после
  десятков итераций качество падает. Годится только чтобы «дожать гейт до зелёного» на одной задаче.
  Для потока из N задач `/loop` не использовать.
- **Читать в начале итерации:** `AGENTS.md`, свой бриф, `artifacts/loop_state.json`, последний
  `artifacts/rounds/round_NN.md`, `git log --oneline -5`. Всё, что не в этих файлах — не существует.
- **Писать в конце итерации:** раунд-артефакт (или комментарий в карточку) с командой, выводом и
  exit-кодом. Знание, оставшееся только в контексте, теряется вместе с ним.
- **Ремонт не бесконечен:** одна и та же команда, красная третий раз подряд, — это стоп и сдача с
  выводом, а не десятая попытка (лимит закрепляется в брифе и в `verify`, см. PLANS.md п.33).

## Роли при fan-out (bounded, ровно четыре)

| Роль | Границы | Артефакт |
|---|---|---|
| explorer | read-only, карта репо и состояние гейта | `handoff/agents/explorer_findings.md` |
| reviewer | read-only, оспаривает слабое evidence | `handoff/agents/reviewer_risks.md` |
| worker | scoped edit, минимальная правка по evidence | `handoff/agents/worker_changes.md` |
| evaluator | верификация, прогон гейта | `handoff/agents/evaluator_verification.md` |
| supervisor (Hermes) | собирает evidence в одно решение | `handoff/supervisor_synthesis.md` |

`ywcrew panel` для reviewer, `ywcrew run --mode edit` для worker, read-only для explorer/evaluator.
Никаких прямых вызовов CLI-агентов — только через ywcrew.

Основной worker по умолчанию — `harness` (DeepSeek Harness, модель `deepseek-v4.1-flash` через
провайдера `opencode-go`): `ywcrew run --backend harness --mode edit`. DSH выполняет команды без
авто-отказов, но **песочницы в `dsh headless` нет** — read-only и edit одинаково идут в git-worktree,
поэтому запись в дерево оператора не попадает, а gitignored-состояние приезжает через
`.worktreeinclude`.

## Сколько ревьюеров нужно (цена против независимости)

- **По умолчанию — ОДИН ревьюер**, не панель: `ywcrew run --mode read-only --backend agy
  --model claude-sonnet-4-6` (он в живом прогоне сам перепрогнал build+lint+test и снял возражение
  фактом). Панель из трёх моделей стоит ~3× токенов и времени ревью.
- **Панель — только для высокой ставки**: релиз, безопасность, архитектурные решения, крупный PR,
  или когда предыдущий вердикт оспорен. Три семейства моделей нужны там, где цена ошибки выше цены
  ревью.
- Почему не «одной модели всегда достаточно»: в первом же живом PR-прогоне три члена панели дали
  ACCEPT / REJECT / «нет вердикта». Одна модель = монетка по вопросу «принимать или нет». При этом
  REJECT был по существу (неполные доказательства), и его снял именно перепрогон гейтов, а не голос.

## Доказательства воркера и консенсус панели (уроки живого PR-прогона)

- **Бандл доказательств = все гейты, которые требует `AGENTS.md` репозитория, а не подмножество.**
  Воркер, доказавший только `go build`, получил законный REJECT: репозиторий требовал ещё
  `golangci-lint run ./...` и `go test -count=1 ./...` перед коммитом. Правило переехало **в сам бриф**:
  бриф рендерит `scripts/worker_brief.py` из `configs/repo_profiles.json` (команды + файл-источник
  требования + формат транскрипта + output-контракт), а `worker_brief.py verify --profile <p>
  --evidence <файл>` печатает `WORKER_EVIDENCE_PASS_0001` / `WORKER_EVIDENCE_STOP_0001` и называет
  незапущенные команды, невидимые exit-коды и ненулевые возвраты. Прогонять verify до ревью —
  дешевле, чем получать REJECT и доигрывать доказательства после.
- **Бриф — это тело задачи в kanban, а не отдельный документ.** `scripts/sync_issues_to_kanban.py`
  берёт open issues (`gh`), отсеивает невалидные машино-проверяемым подмножеством (labels, объём тела,
  наличие acceptance-критериев; семантический триаж остаётся роли), и создаёт задачу с брифом как
  телом, идемпотентно по ключу `gh-<owner>-<repo>-<n>`. `--apply` отказывает, если у профиля не задан
  workspace/project: очередь, которую некому исполнить, — не очередь.
- **Ревьюер, который перепрогоняет гейты сам, сильнее ревьюера, который судит по присланному.**
  В том же прогоне второй член панели сам прогнал build+lint+test в отдельном worktree ветки и снял
  возражение фактом. Разрыв «доказательства неполные» закрывается не спором, а прогоном гейтов на
  head ветки (отдельный `git worktree` того же коммита — доказательство привязано к ревизии).
- **Exit-код принадлежит своей команде.** Требовать `exit=0` отдельной строкой *внутри блока этой
  команды* (до следующей команды). Свободное окно «N строк после команды» пропускает один хвостовой
  `exit=0`, который доказывает все гейты сразу — это нашёл живой ревьюер в первом же прогоне этапа 6,
  и это ровно тот дефект, ради которого бандл и заводился. Регресс-кейс: транскрипт со всеми командами
  и одним кодом в конце должен краснеть.
- **Бандл — пол, а не доказательство полноты.** Список команд в профиле всегда может быть неполным,
  поэтому в профиле хранится `bundle_source` (файл + раздел, откуда гейты взяты), а воркер обязан
  перевывести список из источника и назвать гейты, которые он прогнал сверх списка. Гейт проверяет
  наличие `bundle_source` и этой инструкции в брифе; сама полнота остаётся человекочитаемым остатком.
- **Триаж-лейбл — это решение роли, а не критерии.** `classify()` в мосте называет основание вердикта
  (секция acceptance-критериев vs лейбл), а бриф требует от воркера назвать конкретные критерии, против
  которых он работал. Иначе «очередь валидна» и «работа проверяема» — разные утверждения.
- **Реальность воркспейса важнее брифового идеала.** Kanban-задача с `--project` приезжает воркеру уже
  как git-worktree с собственной ветвью, а `gh` в окружении воркера может быть не авторизован: пуш по SSH
  работает, PR открывает оркестратор из транскрипта. Бриф, требующий конкретного имени ветки и
  собственноручного PR, отправляет воркера в тупик — проверено на первом же живом прогоне.
- **Повторный прогон команды — это тоже её результат.** Проверять все вхождения команды, а не первое:
  «прошло, потом упало» — это упавший гейт, спрятанный за первым успехом (нашёл второй живой ревьюер).
  И `NOT RUN` должен ловиться в любом месте блока команды, а не в первых трёх строках.
- **Валидатор честно объявляет свою терпимость.** Наш валидатор мягче буквы брифа по префиксу промпта
  (`$` необязателен) и по написанию exit-кода (`exit code: 0`, `Exit=0`) — это записано как осознанная
  терпимость, а не выдаётся за строгость: ревьюер должен видеть, где правило строгое, а где снисходительное.
- **Надёжность движков на ревью различается, и это часть evidence.** В одном и том же раунде
  `harness:deepseek-v4.1-flash` (read-only) дал конформный вердикт с четырьмя MINOR, `codex` упирался в
  квоту, `agy` дважды ушёл в таймаут на 900 с (крупная задача), `grok` дважды вернул преамбулу вместо
  вердикта. Планировать ревью с запасным движком и фиксировать «нет вердикта» как отсутствие голоса.
  Отдельно про agy: read-only **выполняет** команды — проверено на двух моделях (claude-sonnet-4-6:
  точный sha256, живой timestamp, exit code 7; gemini-3.8-flash: то же плюс прогон строгого гейта с
  `LOOP_ENGINEERING_PASS_0001` и exit 0). Значит `contract_violated` у gemini-3.8-flash означал ответ,
  не попавший в контракт, а не неспособность. Два таймаута на 900 с дала ширина задачи: agy раскладывает
  широкую задачу на фоновые подзадачи и уходит в ожидание до 20 минут. Лимит ywcrew на ран поднят до
  1 800 000 мс (30 мин) и стал конфигурируемым — `defaults.timeoutMs` в `~/.ywcrew/config.json`,
  приоритет у явного `timeoutMs` в задаче. Панель ywcrew: `harness` + `agy` + `codex` (grok выключен).
- **Несоответствующий output-контракту ответ члена панели = «нет вердикта», а не голос.** Один член
  вернул преамбулу вместо вердикта; в наивном большинстве это исказило бы консенсус. Требовать
  минимум два конформных вердикта, прежде чем объявлять консенсус.

## Два вердикта и время (этапы 7)

- **Продуктовая приёмка — отдельный вердикт с отдельным владельцем.** Техгейт отвечает «дисциплинирована
  ли петля», продуктовый (`scripts/check_product.py`) — «может ли пользователь делать работу этим
  продуктом». Смешав их, получаешь зелёный техгейт над продуктом, который не стартует. У каждого сценария
  обязательна строка `why` — последствие для пользователя; сценарий без неё не принимается (D11).
- **Ожидания измеряются до того, как записываются.** Все сценарии sample-service сначала проверены руками
  (200 у проб, Prometheus-текст у метрик, exit 1 с именем поля у невалидной конфигурации, ~250 мс на
  SIGTERM) и только потом записаны. Первый же живой прогон гейта нашёл дефект в самом гейте — сценарий
  невалидного порта перекрывался выдачей свободных портов; это и есть цена записи ожиданий заранее.
- **Оценку делает очередь, а не супервизор.** `scripts/estimate_task.py` считает p50/p90 по завершённым
  ранам и предлагает `cap = max(15 мин, round_up(2 × p90))` при ≥3 измерениях; при меньшем числе ранов —
  пол и явная пометка. Мост передаёт cap как `--max-runtime`: на cap-е диспетчер убивает воркера и
  пере-ставит задачу, поэтому «работал вечно» — видимый отказ. Оценивать себя — работа того, чью
  оптимизм проверяют, поэтому цифра берётся из истории, а не из обещания.

## Внешний якорь и визуальные проверки (этап 7)

- **Подписывать надо вердикт, а не файл.** Якорь `loop_gate_pass.json` на каждом прогоне получает новый
  `generated_at`, поэтому подпись над файлом умирает на следующем прогоне. Подписывается канонический
  payload (`marker` + `verdict_hash`) — он стабилен, пока стабилен набор вердиктов.
- **`ssh-keygen -Y sign` не перезаписывает существующий `.sig`** (exit 0, старая подпись остаётся на
  месте): после смены вердикта повторная подпись молча верифицировала бы предыдущий. Удалять целевой
  файл подписи перед подписью; регресс R24 держит это.
- **Свидетеля проверяет оператор, а не гейт.** Локальная проверка подписи офлайн (D12), внешняя запись
  (комментарий в `example/sample-service#5`) — отдельный шаг `check-external`, потому что гейт не ходит в сеть.
  Граница честности: ключ на этой же машине доказывает владение ключом, а не независимость; внешняя запись
  делает заметной согласованную перезапись.
- **Визуальная проверка — не «скриншот ради скриншота».** Сценарии требуют минимум один скриншот, а
  evaluator ловит то, чего не видит JSON: первый же vision-разбор нашёл заголовок, обрезанный посреди
  слова без многоточия. Правило проверялось снятием фикса — иначе оно декорация.
- **Headless-браузер обязателен и проверяется гейтом.** Визуальный чек, который молча скипается при
  отсутствии браузера, хуже отсутствия чека (D13 падает, если браузера нет).

## Артефакты

```
artifacts/loop_state.json        состояние петли (round, phase, readiness/evidence/risk, blockers, marker)
artifacts/rounds/round_NN.md     по одному файлу на раунд: gap → change → evidence → metrics → next
artifacts/loop_gate_report.json  машинный вывод гейта (--report)
artifacts/issue_bridge_report.json  что мост сделал с очередью issues (queued / needs-triage / skipped)
handoff/latest_loop.json         маркер, статус, пути артефактов
handoff/supervisor_synthesis.md  один синтез супервизора
configs/repo_profiles.json       контракт репозитория-цели: бандл доказательств, PR-правила, assignee
```

`artifacts/` и `handoff/` — состояние, а не исходники: они в `.gitignore`.

## Инварианты

- Никакого заявления об успехе без воспроизводимой команды или видимого артефакта.
- Ремонт только по релевантным файлам; широкие переписывания запрещены.
- Секреты, ключи и приватные данные в артефакты не попадают.
- Маркер PASS печатает только гейт, не агент.
- Печать вердикта никогда не зависит от возможности записи: если `--report` или якорь не пишутся
  (read-only песочница codex/agy), гейт печатает warning и всё равно выдаёт маркер — гейт, умирающий
  после «9 ok», неотличим от сломанного.
- Метрики в `loop_state.json` не выдумываются: они должны согласовываться с артефактами раундов.

## Маршрутизация ролей по движкам (проверено прогонами)

| Задача | Движок | Почему |
|---|---|---|
| карта репо, чтение, ревью, команды, прогон гейта | `agy` | read-only идёт в git-worktree: команды выполняются, записи не попадают в твоё дерево; gitignored-состояние попадает в worktree через `.worktreeinclude` (`artifacts/`, `handoff/`) — проверено: гейт в worktree даёт 9 ok и PASS |
| прогон проектного гейта, evaluator, всё, что должно видеть реальное дерево | `codex` | нативный read-only sandbox: читает дерево целиком (включая gitignored), запись запрещена |
| второе мнение, независимое ревью, команды | `grok` | read-only разрешает выполнение команд, видит реальное дерево |
| worker по умолчанию: фичи, фиксы, тесты, правки скриптов | `harness` | DeepSeek Harness (`deepseek-v4.1-flash` через `opencode-go`), edit в git-worktree; песочницы нет — изоляцию даёт worktree |
